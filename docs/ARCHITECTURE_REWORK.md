# 译键 · 架构重构方案

> 基线：`v0.18.0-stable`（缓冲模式）。重构期间任何问题都可 `git checkout v0.18.0-stable` 回退。

---

## 一、为什么重构

### 旧架构的核心问题

```
用户按键 → buffer（看不见）→ 点回车 → 候选 → 选中才上屏
```

| 问题 | 后果 |
|---|---|
| 英文不可见 | 用户无法确认自己打了什么 |
| 切走输入框 buffer 被清空 | 输入全部丢失，零预警 |
| 翻译失败只能等或放弃 | 卡死，无重试 |
| 没有撤销 | 误操作不可逆 |

**根因**：为了让「错的内容不发出去」，选择了代价最大的方案——把用户输入从应用里抽走。

---

## 二、新架构：双通道

### 核心原则
**用户永远看得见、掌控得住自己输入的内容。** 翻译是增强，不是门禁。

### 两种输入意图，两条路径

```
                    ┌─────────────────────────────┐
                    │      用户开始输入            │
                    └──────────────┬──────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │  输入的是英文还是中文？       │
                    └──────────────┬──────────────┘
                          ┌────────┴────────┐
                          ▼                 ▼
                  ┌───────────────┐  ┌───────────────┐
                  │   英文通道     │  │   中文通道     │
                  └───────┬───────┘  └───────┬───────┘
                          │                  │
        英文**直接上屏**（用户看得见）    中文**直接上屏**
                          │                  │
                    点回车/「译」        点回车/「译」
                          │                  │
              ┌───────────▼──────────┐   ┌──▼──────────────┐
              │ 原地替换为中文候选    │   │ 转换为地道英文    │
              │ 失败则英文原样保留    │   │ 作为学习参考      │
              └──────────┬───────────┘   └──┬──────────────┘
                         │                  │
                  可撤销（3 秒内）      可选采纳
```

## 三、中文输入问题：产品级解法

### 问题
用户「实在没办法输入英文」时（不懂某个词、不会某个句式），怎么办？

这不是边缘情况，而是**核心用户画像的常态**——英文水平有限的人，卡壳才是日常。

### 分析：卡壳有四种形态

| 形态 | 例子 | 用户想要 |
|---|---|---|
| **词卡壳** | 想不起「期待」的英文 | 一个单词 |
| **句式卡壳** | 知道意思，组不成句 | 一句地道英文 |
| **语域卡壳** | 不知道该正式还是随意 | 不同档位的表达 |
| **完全卡壳** | 只会说中文 | 完整英文表达 |

### 方案：中文直输 + 三档输出

**用户直接打中文**（本来就是母语，零门槛），敲回车后模型给三样东西：

```
用户输入：这个我不太确定，可能得问他一下

┌─────────────────────────────────────────┐
│ 口语    Not sure about this, might need   │  ← 默认，聊天场景
│         to ask him.                       │
├─────────────────────────────────────────┤
│ 中性    I'm not certain about this and     │  ← 邮件/工作
│         may need to check with him.       │
├─────────────────────────────────────────┤
│ 正式    I am not certain regarding this    │  ← 正式场合
│         matter and may need to consult    │
│         him.                              │
└─────────────────────────────────────────┘
```

**关键设计决策**：

1. **中文照常上屏**，不拦截。用户看见自己打的中文，符合输入法直觉。
2. **英文是建议，不是替换**。点选才替换，否则中文留着直接发。
3. **三档语域**解决「不知道正式不正式」的焦虑。
4. **词级卡壳**：中文里夹英文词也能处理（`我 need 一个 suggestion` → 自动补全为完整英文）。

### 为什么不做「翻译模式切换」

考虑过加「中→英模式」开关，否决了：

- 用户不知道什么时候该切
- 模式切换增加认知负担
- **模型有能力自己判断**（输入中文就给英文，输入英文就给中文）

**统一规则**：输入什么语言，就输出另一种语言 + 同语言的地道版本。

## 四、数据流重构

### 旧
```
按键 → buffer → 翻译 → 候选 → 选中 → commitText
         ↑
      不可见、易丢失
```

### 新
```
按键 → commitText（直接上屏，用户可见）
         ↓
     记录 [startPos, endPos, 原文]
         ↓
     点回车 → 翻译（带去重、可重试）
         ↓
   ┌─────┴─────┐
   ▼           ▼
 成功        失败
   │           │
原地替换     原文保留 + 错误提示 + 重试按钮
   │
可撤销（3秒）
```

### 关键数据结构

```kotlin
data class TranslationSpan(
    val start: Int,          // 原文在输入框中的起始位置
    val end: Int,
    val original: String,
    val translated: String?,
    val timestamp: Long,
)
```

**优势**：
- 原文始终在应用里 → 切走不丢
- 有位置信息 → 可精确替换、可撤销
- 失败无损失 → 只是没翻译，不影响发送

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 原地替换位置计算错误 | 替换前用 `getTextBeforeCursor` 校验尾部匹配，不匹配则放弃替换 |
| 替换后用户后悔 | 3 秒撤销窗口，记录被替换的原文 |
| 中文输入时误触发翻译 | 只在明确点「译」或回车时触发 |
| 模型判断语言出错 | 前端预判：含 >= 2 个汉字 → 走中文通道 |
| 重构导致功能倒退 | 每阶段真机验证 + 保留 `v0.18.0-stable` 回退 |

---

## 七、非目标（本阶段不做）

- 离线模型兜底
- 错误小黄点提示
- 多语言支持
- 云端同步

先把核心输入体验做对。
