# 译键 · 架构重构方案

> 基线：`v0.18.0-stable`（缓冲模式）。重构期间任何问题都可 `git checkout v0.18.0-stable` 回退。

---

## 一、为什么重构

### 旧架构的核心问题

```
用户按键 → buffer（看不见）→ 点回车 → 候选 → 选中才上屏
```

| 问题 | 后果 |
|---|---|
| 英文不可见 | 用户无法确认自己打了什么 |
| 切走输入框 buffer 被清空 | 输入全部丢失，零预警 |
| 翻译失败只能等或放弃 | 卡死，无重试 |
| 没有撤销 | 误操作不可逆 |

**根因**：为了让「错的内容不发出去」，选择了代价最大的方案——把用户输入从应用里抽走。

---

## 二、新架构：双通道

### 核心原则
**用户永远看得见、掌控得住自己输入的内容。** 翻译是增强，不是门禁。

### 两种输入意图，两条路径

```
                    ┌─────────────────────────────┐
                    │      用户开始输入            │
                    └──────────────┬──────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │  输入的是英文还是中文？       │
                    └──────────────┬──────────────┘
                          ┌────────┴────────┐
                          ▼                 ▼
                  ┌───────────────┐  ┌───────────────┐
                  │   英文通道     │  │   中文通道     │
                  └───────┬───────┘  └───────┬───────┘
                          │                  │
        英文**直接上屏**（用户看得见）    中文**直接上屏**
                          │                  │
                    点回车/「译」        点回车/「译」
                          │                  │
              ┌───────────▼──────────┐   ┌──▼──────────────┐
              │ 原地替换为中文候选    │   │ 转换为地道英文    │
              │ 失败则英文原样保留    │   │ 作为学习参考      │
              └──────────┬───────────┘   └──┬──────────────┘
                         │                  │
                  可撤销（3 秒内）      可选采纳
```

## 三、语言问题：只有一条通道

### 结论先行

**不做语种判断、不做通道分叉、不做词级解析。** 不管用户输入中文、英文还是混杂，客户端永远做同一件事：

```
任意输入
    │
    ▼  原样发给模型
┌───────────────────────────┐
│  中文候选（点选 → 上屏）    │
│  地道英文（教师版，仅参考）  │
└───────────────────────────┘
```

### 为什么这样是对的

| 场景 | 中文候选 | 教师版 |
|---|---|---|
| `i want eat apple` | 我想吃个苹果。 | I want to eat an apple. |
| `这个我不太确定，得问他` | 这个我不太确定，得问他一下。 | I'm not sure about this — I'll need to ask him. |
| `I need 一个 suggestion` | 我需要一个建议。 | I need a suggestion. |
| `尴尬` | 有点尴尬。 | That's a bit awkward. |

**用户看到的两样东西永远是同一对**：要发出去的中文 + 要学的英文。输入语言只是决定这两样各自「从哪来」，不需要用户关心，也不需要客户端判断。

### 为什么之前想复杂了

我一度设计了三通道（纯英文 / 混合 / 纯中文），理由是「词级卡壳和句级卡壳要区别对待」。但这是**把客户端的分类能力当成了产品能力**：

- 模型本身能处理中英混排，不需要先分类
- 分类规则（汉字占比阈值）必然误判，且误判后用户无法纠正
- 每多一个分支就多一条出错路径

**一条路径 + 两个输出，比三条路径 + 各自逻辑更可靠。**

### 输入法层面的意义

用户卡壳时可以随时切中文输入法，不需要：
- 记住当前是什么模式
- 手动切换「翻译方向」
- 担心整句话被当成中文

打完了点回车，该给的都会给。

### 唯一需要客户端做的判断

只有一条：**内容是否为空/全是标点**（不值得发请求）。这不是语种判断，是发送前的健全性检查。

## 四、数据流重构

### 旧
```
按键 → buffer → 翻译 → 候选 → 选中 → commitText
         ↑
      不可见、易丢失
```

### 新
```
按键 → commitText（直接上屏，用户可见）
         ↓
     记录 [startPos, endPos, 原文]
         ↓
     点回车 → 翻译（带去重、可重试）
         ↓
   ┌─────┴─────┐
   ▼           ▼
 成功        失败
   │           │
原地替换     原文保留 + 错误提示 + 重试按钮
   │
可撤销（3秒）
```

### 关键数据结构

```kotlin
data class TranslationSpan(
    val start: Int,          // 原文在输入框中的起始位置
    val end: Int,
    val original: String,
    val translated: String?,
    val timestamp: Long,
)
```

**优势**：
- 原文始终在应用里 → 切走不丢
- 有位置信息 → 可精确替换、可撤销
- 失败无损失 → 只是没翻译，不影响发送

## 五、分阶段实施

| 阶段 | 内容 | 可回退点 |
|---|---|---|
| **S1** | 英文直上屏 + 原地替换 + 撤销 | `v0.18.0-stable` |
| **S2** | 单通道模型：中文输入也走同一条路径 | tag `v0.19.0-single-path` |
| **S3** | 失败重试 + 翻译超时 | tag `v0.19.1-retry` |
| **S4** | 报告改为应用内可见 | tag `v0.20.0-report` |

每阶段独立可回退，不追求一次性完成。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 原地替换位置计算错误 | 替换前用 `getTextBeforeCursor` 校验尾部匹配，不匹配则放弃替换 |
| 替换后用户后悔 | 3 秒撤销窗口，记录被替换的原文 |
| 中文输入时误触发翻译 | 只在明确点「译」或回车时触发 |
| 模型对混排输入理解偏差 | 提示词明确要求「按用户真实意图输出，不要机械直译」，并对混合输入给出例句 |
| 重构导致功能倒退 | 每阶段真机验证 + 保留 `v0.18.0-stable` 回退 |

---

## 七、非目标（本阶段不做）

- 离线模型兜底
- 错误小黄点提示
- 多语言支持
- 云端同步

先把核心输入体验做对。
